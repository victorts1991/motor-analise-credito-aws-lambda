# Spec 00 — Constituição e Convenções do Projeto

- **Status:** Implementada
- **Objetivo:** definir as regras que valem para todo o projeto: princípios, fluxo de trabalho com specs, convenções de código, stack permitida, modelo de spec e definição de pronto. Toda outra spec e todo código seguem este documento.
- **Depende de:** [README](../../README.md), [ADR 0001](../../docs/adr/0001-invocacao-sincrona-entre-lambdas.md), [ADR 0002](../../docs/adr/0002-runtime-dotnet10-gerenciado-vs-native-aot.md), [ADR 0003](../../docs/adr/0003-emulador-local-localstack.md), [ADR 0004](../../docs/adr/0004-idempotencia-e-publicacao-no-kafka.md)

---

## 1. Regras de Negócio (RN)

Nesta spec, as regras são **regras do projeto**: valem para todas as outras specs e não podem ser contrariadas sem alterar esta spec antes.

- **RN-01 — A spec é a fonte da verdade.** Nenhum código é escrito sem uma spec com status `Aprovada`. Se o código precisar divergir da spec, a spec é corrigida primeiro e o código depois.
- **RN-02 — Uma spec por vez.** As specs são implementadas na ordem numérica, cada uma em uma branch própria e em um PR próprio.
- **RN-03 — Domínio puro.** O projeto `MotorCredito.Dominio` não referencia AWS SDK, MongoDB, Kafka nem qualquer biblioteca de I/O.
- **RN-04 — Idempotência obrigatória.** Todo processamento de mensagem do Kafka é idempotente, seguindo a [ADR 0004](../../docs/adr/0004-idempotencia-e-publicacao-no-kafka.md).
- **RN-05 — Clientes criados uma vez.** `MongoClient`, `IProducer` e `AmazonLambdaClient` são criados uma única vez por instância da Lambda, fora do handler, e reaproveitados entre invocações.
- **RN-06 — Dados sensíveis protegidos.** O CPF nunca aparece completo em log, mensagem de erro ou resposta HTTP. A regra de mascaramento é definida na spec 05.
- **RN-07 — Configuração por variável de ambiente.** Endpoints, nomes de tópicos, nomes de funções e credenciais vêm de variáveis de ambiente. Nada disso fica fixo no código. O arquivo `.env` nunca é commitado; o `.env.example` documenta todas as variáveis.
- **RN-08 — Execução 100% local.** O projeto roda com `docker compose` na máquina do desenvolvedor. Não existe pipeline de CI/CD nem deploy em conta AWS.
- **RN-09 — Rastreabilidade de testes.** Todo `RN`, `CA` e `EC` de uma spec é coberto por pelo menos um teste automatizado, e a seção **Testes** da spec indica qual teste cobre cada item. Quando o item depende de ferramenta externa ou do ambiente (scripts, Docker, LocalStack), ele pode ser coberto por uma **verificação manual**, descrita passo a passo na seção **Testes**, com o comando e o resultado esperado.
- **RN-10 — Decisões arquiteturais viram ADR.** Uma decisão que muda a arquitetura gera uma nova ADR em `docs/adr/`. ADRs aceitas não são editadas; uma decisão nova substitui a antiga com o status `Substituída pela ADR NNNN`.

---

## 2. Comportamento Esperado

Fluxo para implementar qualquer spec, seja por uma pessoa ou pelo Copilot.

### Antes de começar

1. Ler `_context/memory.md` para saber o estado atual do projeto.
2. Ler a spec inteira e todos os arquivos listados em **Depende de**.
3. Confirmar que todas as specs das quais ela depende estão com status `Implementada`.
4. Criar a branch `spec/NN-descricao-curta` (exemplo: `spec/06-motor-regras-score`).

### Durante a implementação

1. Implementar **somente** o que a spec descreve. O que estiver em **Non-Goals** não é feito.
2. Se faltar informação ou houver ambiguidade, **parar e perguntar**, em vez de inventar uma regra.
3. Escrever os testes junto com o código, seguindo a seção **Testes** da spec.

### Ao terminar (definição de pronto)

A spec só está pronta quando **todos** os itens abaixo forem verdadeiros:

- [ ] `dotnet build` termina sem erros e sem warnings.
- [ ] `dotnet test` passa por completo.
- [ ] Todo `CA` da spec foi verificado.
- [ ] Todo `RN`, `CA` e `EC` tem pelo menos um teste citado na seção **Testes**.
- [ ] O status da spec foi alterado para `Implementada`.
- [ ] O `_context/memory.md` foi atualizado.
- [ ] Uma entrada foi adicionada ao `_context/changelog.md`.
- [ ] Se algum comando ou passo de execução mudou, o `README.md` foi atualizado.

### 4.3 Nomenclatura

- **Termos do domínio em português**, seguindo a linguagem do negócio: `Proposta`, `AvaliacaoScore`, `FaixaRisco`, `LimiteAprovado`.
- **Sufixos técnicos do .NET em inglês**, como é padrão na plataforma: `Request`, `Response`, `Client`, `Repository`, `Options`, `Exception`, `Async`, `Tests`.
  - Exemplos: `AvaliacaoScoreRequest`, `IMotorScoreClient`, `IPropostaRepository`, `PropostaNaoEncontradaException`.
- Classes, métodos e propriedades em `PascalCase`; parâmetros e variáveis locais em `camelCase`; campos privados em `_camelCase`.
- Métodos com I/O são assíncronos e terminam em `Async`.
- **JSON** (eventos Kafka, respostas HTTP) e **campos do MongoDB** em `camelCase` português: `idProposta`, `valorSolicitado`.
- **Valores de enum** serializados como texto em `MAIUSCULO_COM_UNDERSCORE`: `EM_PROCESSAMENTO`, `APROVADA`, `BAIXO`.
- **Variáveis de ambiente** em `MAIUSCULO_COM_UNDERSCORE`: `MONGODB_URI`, `KAFKA_BOOTSTRAP_SERVERS`.

### 4.4 Padrões de código

- **Handler das Lambdas:** a classe `Function` tem dois construtores:
  - um **sem parâmetros**, usado pelo runtime da Lambda, que monta as dependências reais;
  - um que **recebe as dependências por parâmetro**, usado pelos testes.
- **Sem container de injeção de dependência.** A composição é manual, no construtor sem parâmetros.
- **Serialização:** `System.Text.Json` com `JsonSerializerContext` (*source generator*) sempre que possível ([ADR 0002](../../docs/adr/0002-runtime-dotnet10-gerenciado-vs-native-aot.md)).
- **Valores monetários:** sempre `decimal`, nunca `double` ou `float`. No MongoDB, armazenados como `Decimal128`.
- **Datas:** sempre em UTC, obtidas por um `TimeProvider` injetado. Nunca usar `DateTime.Now` ou `DateTime.UtcNow` diretamente, para que os testes controlem o tempo. No JSON, formato ISO 8601.
- **Erros:** exceções de domínio específicas (herdando de uma base comum do projeto). Nenhuma exceção é engolida em silêncio; toda exceção capturada é registrada em log.
- **Logs:** estruturados, sem dados sensíveis (detalhes na spec 05).

### 4.5 Convenções de testes

- Padrão **Arrange / Act / Assert**, com as três partes separadas por uma linha em branco.
- Nome do teste: `Deve_<resultado>_Quando_<condicao>`. Exemplo: `Deve_retornar_404_Quando_proposta_nao_existe`.
- Testes de integração marcados com `[Trait("Category", "Integracao")]`, para o filtro do README funcionar.
- Testes de arquitetura marcados com `[Trait("Category", "Arquitetura")]`. Eles verificam as regras de referência entre projetos e a lista de pacotes proibidos lendo os arquivos `.slnx`, `.csproj` e `.props` do repositório, e são os únicos testes automatizados que podem ler arquivos do repositório.
- Um teste verifica um comportamento. Casos com a mesma lógica e dados diferentes usam `[Theory]` com `[InlineData]`.

### 4.6 Git

- **Branch:** `spec/NN-descricao-curta`.
- **Commits:** padrão [Conventional Commits](https://www.conventionalcommits.org/), em português e com uma linha. Tipos usados: `feat`, `fix`, `test`, `docs`, `refactor`, `chore`.
  - Exemplo: `feat: implementa cálculo de score no motor de regras`.
- **PR:** um por spec, com o título `Spec NN — <título da spec>` e a checklist da definição de pronto (seção 2) na descrição.

- Verificações manuais recebem identificadores próprios (`VM-01`, `VM-02`...) e aparecem na tabela da seção **5. Testes** com o tipo `manual`.

## 8. Edge Cases

- **EC-01 — Spec ambígua ou incompleta.** Quem implementa para e pergunta. A resposta é incorporada à spec antes de continuar o código.
- **EC-02 — Código precisa divergir da spec.** A spec é alterada primeiro, no mesmo PR, com a mudança explicada na descrição (RN-01).

- **EC-04 — Spec depende de outra ainda não implementada.** A implementação não começa até a dependência estar `Implementada`.
- **EC-05 — Uma decisão de arquitetura muda.** Cria-se uma nova ADR que substitui a anterior; a ADR antiga só tem o status alterado (RN-10).
- **EC-06 — Conflito entre esta spec e outra.** Esta spec prevalece, e a outra é corrigida.

# Spec 01 — Estrutura da Solution e Empacotamento .NET

- **Status:** Implementada
- **Objetivo:** criar a solution, os projetos .NET e as configurações compartilhadas, deixar as quatro Lambdas compilando com um handler esqueleto e gerar um pacote `.zip` por Lambda com um único script. As regras de arquitetura da spec 00 passam a ser verificadas por testes automatizados.
- **Depende de:** [Spec 00](./00_especificacao-constituicao-e-convencoes.md), [ADR 0002](../../docs/adr/0002-runtime-dotnet10-gerenciado-vs-native-aot.md)

---

## 1. Regras de Negócio (RN)

- **RN-01 — Solution única.** Existe uma única solution, `MotorAnaliseCredito.slnx`, na raiz do repositório, contendo todos os projetos de `src/` e `tests/`.
- **RN-02 — SDK fixado.** Um `global.json` na raiz fixa o SDK do .NET 10. Uma máquina com outros SDKs instalados (como o .NET 11) usa o SDK 10 dentro do repositório.
- **RN-03 — Propriedades comuns centralizadas.** `TargetFramework`, `Nullable`, `ImplicitUsings` e `TreatWarningsAsErrors` são definidos uma única vez, no `Directory.Build.props` da raiz. Nenhum `.csproj` redefine essas propriedades.
- **RN-04 — Versões de pacotes centralizadas.** As versões de todos os pacotes NuGet ficam no `Directory.Packages.props` da raiz (*Central Package Management*). Nenhum `.csproj` informa versão em `PackageReference`.
- **RN-05 — Projetos e referências.** Os projetos e as referências entre eles seguem exatamente a seção 3 da spec 00.
- **RN-06 — Lambdas com handler esqueleto.** Cada projeto de Lambda é uma biblioteca de classes com as propriedades de Lambda e uma classe `Function` com um handler esqueleto, que só devolve um texto identificando a função. Os handlers reais são criados nas specs 06 a 09.
- **RN-07 — Empacotamento por script único.** O script `scripts/empacotar-lambdas.sh` gera um `.zip` por Lambda em `dist/`, com o nome da função (`dist/motor-regras-score.zip`, por exemplo).
- **RN-08 — Arquitetura configurável.** A arquitetura dos pacotes vem da variável `LAMBDA_ARCHITECTURE` (`x86_64` ou `arm64`), com `x86_64` como padrão. A variável é documentada no `.env.example`.
- **RN-09 — Regras de arquitetura testadas.** As regras de referência entre projetos e a lista de pacotes proibidos da spec 00 são verificadas por testes automatizados no projeto `MotorCredito.Arquitetura.Tests`.

---

## 2. Comportamento Esperado

Do ponto de vista de quem clona o repositório:

1. Na raiz, `dotnet --version` mostra uma versão `10.0.x`, mesmo que a máquina tenha outros SDKs.
2. `dotnet build` compila os 11 projetos sem erros e sem warnings.
3. `dotnet test` executa os testes dos quatro projetos de Lambda e os testes de arquitetura, e todos passam.
4. `./scripts/empacotar-lambdas.sh`:
   1. carrega o `.env`, se existir;
   2. valida `LAMBDA_ARCHITECTURE` (usa `x86_64` se ausente);
   3. confere se o `dotnet` e o Amazon.Lambda.Tools estão instalados;
   4. cria a pasta `dist/`, se não existir;
   5. empacota as quatro Lambdas, uma por vez, mostrando o nome de cada uma;
   6. termina mostrando a lista dos `.zip` gerados.
5. Se qualquer etapa do script falhar, ele para na hora, mostra uma mensagem clara e termina com código de saída diferente de zero.

- Sobrescreve pacotes antigos com o mesmo nome.
- Ao final, lista os arquivos de `dist/`.

# Regras para o código C# em `src/`

Estas regras complementam a [spec 00](../../_context/specs/00_especificacao-constituicao-e-convencoes.md). Em caso de conflito, a spec 00 prevalece.

## Estilo

- Use *file-scoped namespace* (`namespace MotorCredito.Dominio;`).
- Classes são `sealed` por padrão. Só deixe uma classe aberta para herança quando houver um motivo.
- Use `record` para contratos e DTOs (eventos, requests, responses).
- Respeite o *nullable*: não use o operador `!` para silenciar avisos. Trate o caso nulo.
- Comentários em português, e só para explicar **por que** algo é feito, nunca **o que** o código já diz.

## Projeto `MotorCredito.Dominio`

- Sem nenhuma referência a AWS SDK, MongoDB, Kafka, HTTP ou sistema de arquivos.
- Regras de negócio em métodos puros: mesma entrada, mesma saída, sem efeitos colaterais.
- Dependências externas (repositórios, clientes) existem aqui só como **interfaces**.

## Handlers das Lambdas (`MotorCredito.Lambda.*`)

- A classe `Function` tem dois construtores:
  - **sem parâmetros**: usado pelo runtime da Lambda; monta as dependências reais;
  - **com parâmetros**: recebe as dependências; usado pelos testes.
- O handler só orquestra: desserializa a entrada, chama o domínio ou os serviços e monta a saída. Regra de negócio não fica no handler.
- Clientes de infraestrutura (`MongoClient`, `IProducer`, `AmazonLambdaClient`) são criados **uma vez** e guardados em campo estático ou de instância, nunca dentro do método do handler.
- Variáveis de ambiente são lidas **uma vez**, na inicialização. Se uma variável obrigatória estiver ausente, lance uma exceção clara com o nome da variável, para a falha aparecer logo no *cold start*.
- Métodos com I/O são `async` e terminam em `Async`. Nunca use `.Result` ou `.Wait()`.
- O producer Kafka faz `Flush` antes de o handler retornar.

## Dados e tempo

- Valores monetários sempre em `decimal`.
- Datas sempre em UTC, obtidas de um `TimeProvider` recebido por injeção. Nunca use `DateTime.Now` nem `DateTime.UtcNow`.

## Erros e logs

- Use exceções de domínio específicas, herdando da exceção base do projeto.
- Nunca capture uma exceção sem registrar em log ou relançar.
- Nunca escreva o CPF completo em log, exceção ou resposta. Use a rotina de mascaramento da spec 05.
- Não use `Console.WriteLine` para log; use o mecanismo definido na spec 05.

# Regras para os testes em `tests/`

Estas regras complementam a [spec 00](../../_context/specs/00_especificacao-constituicao-e-convencoes.md), seção 4.5. Em caso de conflito, a spec 00 prevalece.

## Ferramentas

- Framework: **xUnit**.
- Mocks: **NSubstitute** (`Substitute.For<T>()`). Nunca use Moq.
- Asserções: **Shouldly** (`resultado.ShouldBe(...)`). Nunca use FluentAssertions nem `Assert.*` do xUnit.
- Integração: **Testcontainers** para MongoDB e Kafka reais.

## Estrutura de cada teste

- Nome no formato `Deve_<resultado>_Quando_<condicao>`, em português.

# ADR 0001 — Invocação síncrona entre Lambdas (processador → motor de score)

- **Status:** Aceita
- **Data:** 2026-11-21

## Contexto

O cálculo de score é uma regra de negócio determinística: a mesma entrada sempre produz a mesma saída e não precisa de banco nem de rede. Queremos que essa regra fique isolada, testável sem nenhum mock de infraestrutura e com ciclo de deploy independente do restante da esteira.

A Lambda `processador-proposta` precisa do resultado do score **antes** de gravar a decisão e publicar o evento `credito.propostas.avaliadas`. Ou seja, o fluxo depende da resposta e não pode seguir sem ela.

## Decisão

O `processador-proposta` invoca a Lambda `motor-regras-score` de forma **síncrona** (`InvocationType = RequestResponse`) via `AWSSDK.Lambda`.

Regras que acompanham a decisão:

1. **Contrato explícito.** Entrada `AvaliacaoScoreRequest` e saída `AvaliacaoScoreResponse` ficam no projeto `MotorCredito.Dominio`, compartilhado pelas duas Lambdas.
2. **Abstração no chamador.** O processador depende de uma interface (`IMotorScoreClient`), não do SDK diretamente. A implementação padrão usa `AmazonLambdaClient`; trocar por uma chamada em memória exige só outra implementação da interface.
3. **Tratamento de erro.** Uma exceção dentro do motor não vira exceção HTTP no chamador: o `Invoke` retorna sucesso com o campo `FunctionError` preenchido. O cliente deve verificar `FunctionError` e transformar em exceção de domínio.
4. **Timeouts encadeados.** O timeout do processador deve ser maior que o do motor somado à latência da chamada, para o processador nunca morrer esperando.
5. **Cliente reaproveitado.** O `AmazonLambdaClient` é criado uma única vez, fora do handler.

## Alternativas consideradas

| Alternativa | Por que não agora |
| --- | --- |
| **Motor como biblioteca dentro do processador** (chamada em memória) | É a opção mais barata e simples, e provavelmente a recomendada em produção. Fica descartada **só para a POC**, porque o objetivo é treinar a comunicação entre Lambdas. A interface `IMotorScoreClient` mantém essa troca a uma implementação de distância. |
| **AWS Step Functions** orquestrando as etapas | Resolve orquestração e retries de forma declarativa, mas adiciona um serviço a mais para emular e estudar. Fica para uma evolução futura. |
| **Comunicação assíncrona via Kafka** (tópico de pedido de score e tópico de resposta) | Desacopla totalmente, mas exige correlação de mensagens e torna o fluxo bem mais complexo para um cálculo que leva milissegundos. |

## Consequências

**Positivas**

- O domínio fica isolado de verdade: a Lambda do motor não referencia o projeto de infraestrutura.
- O motor pode ser testado só com dados de entrada e saída.
- O time pratica invocação entre Lambdas, contratos compartilhados e tratamento de `FunctionError`.

**Negativas (e conhecidas)**

- **Custo duplicado:** enquanto o motor executa, o processador fica parado aguardando e também é cobrado. A AWS documenta esse padrão como antipadrão para produção.
- **Cold start em cadeia:** se as duas Lambdas estiverem frias, as latências se somam.
- **Acoplamento temporal:** se o motor estiver indisponível, o processador falha e o lote do Kafka é reentregue. A idempotência (ADR 0004) garante que isso não gere duplicidade.

## Quando revisitar

Antes de levar o padrão para produção, ou se as medições de latência e custo mostrarem que a chamada síncrona é um gargalo. Nesse caso, a primeira opção é a alternativa da biblioteca em memória.

# ADR 0002 — Runtime gerenciado `dotnet10` em vez de Native AOT

- **Status:** Aceita
- **Data:** 2026-11-21

## Contexto

As Lambdas serão escritas em C#. Na AWS existem dois caminhos principais para .NET:

1. **Runtime gerenciado** (`dotnet10`): a AWS fornece e atualiza o runtime; publicamos só as DLLs da aplicação.
2. **Native AOT**: o código é compilado para binário nativo e roda no runtime `provided.al2023` (runtime customizado). O cold start costuma cair bastante, mas exige trimming, serialização JSON por *source generator* e bibliotecas compatíveis com AOT.

Pontos que pesam na decisão:

- O **.NET 8** chega ao fim de suporte no Lambda em **novembro de 2026**. O **.NET 10** é a versão LTS atual, com suporte no Lambda até **novembro de 2028**.
- O LocalStack suporta o runtime `dotnet10` desde a versão 4.13.
- Nem todas as bibliotecas do projeto têm compatibilidade garantida com trimming/AOT (`MongoDB.Driver` e `Confluent.Kafka` precisam ser validadas).
- Quem clonar o projeto pode estar em uma máquina `x86_64` ou `arm64` (como Macs com Apple Silicon).

## Decisão

- Usar o **runtime gerenciado `dotnet10`**, com `TargetFramework` `net10.0`.
- Fixar o SDK 10 no repositório com um `global.json` (a máquina pode ter outros SDKs instalados, como o 11).
- Usar **`x86_64`** como arquitetura padrão das Lambdas, configurável pela variável `LAMBDA_ARCHITECTURE` no `.env` (`x86_64` ou `arm64`). Quem estiver em uma máquina `arm64` troca o valor e evita que o LocalStack precise emular outra arquitetura.
- Serializar com `Amazon.Lambda.Serialization.SystemTextJson`. Sempre que possível, usar um `JsonSerializerContext` (*source generator*) desde o início, para não fechar a porta do AOT no futuro.

## Alternativas consideradas

| Alternativa | Por que não agora |
| --- | --- |
| **Native AOT** (`provided.al2023`) | Melhor cold start, mas aumenta muito a complexidade de build e exige validar a compatibilidade de cada biblioteca. O foco da POC é a arquitetura orientada a eventos, não a otimização de inicialização. |
| **.NET 8** gerenciado | Fim de suporte no Lambda em novembro de 2026. Começar um projeto novo nele não faz sentido. |
| **.NET 11** | Não é LTS e não tem runtime gerenciado no Lambda. |
| **Imagem de container** em vez de `.zip` | Útil para pacotes grandes ou dependências nativas, que não é o caso. O `.zip` é mais simples de carregar no LocalStack. |

## Consequências

**Positivas**

- Build e empacotamento simples com `dotnet lambda package`.
- Nenhuma restrição de reflection ou trimming nas bibliotecas.
- Runtime com suporte até 2028.

**Negativas**

- Cold start maior que o do AOT. Para uma POC local isso não é problema, mas precisa ser medido antes de produção.
- Na AWS real, `arm64` (Graviton) costuma sair mais barato que `x86_64`. A escolha de arquitetura deve ser revista no deploy.

## Quando revisitar

- Ao preparar um deploy real: medir cold start e avaliar Native AOT ou SnapStart, além de `arm64`.
- Quando a AWS anunciar o próximo runtime .NET LTS.

# ADR 0004 — Idempotência e publicação no Kafka (escrita dupla)

- **Status:** Aceita
- **Data:** 2026-11-21

## Contexto

O Kafka, via Event Source Mapping, entrega mensagens **pelo menos uma vez** (*at-least-once*): se a Lambda falhar ou estourar o timeout, o lote inteiro é entregue de novo.

A Lambda `processador-proposta` faz duas escritas em sistemas diferentes:

1. Grava a decisão no **MongoDB** (coleção `propostas`).
2. Publica a decisão no **Kafka** (tópico `credito.propostas.avaliadas`).

Não existe transação que englobe MongoDB e Kafka juntos. Se a Lambda gravar no Mongo e cair antes de publicar, uma reentrega que simplesmente "pula propostas já processadas" faria o evento **sumir**.

## Decisão

### 1. Chave e índices

- A chave de idempotência é o **`idProposta`**.
- A coleção `propostas` tem **índice único** em `idProposta`.
- A coleção `auditoria_propostas` tem **índice único composto** em `idProposta` + `evento`.
- A mensagem Kafka é publicada com **chave = `idProposta`**, para que todos os eventos de uma proposta caiam na mesma partição e sejam processados em ordem.

### 2. Estados da proposta

```text
EM_PROCESSAMENTO → APROVADA | REPROVADA
                         └─ publicadoEm preenchido quando o Kafka confirmar a publicação
```

O documento nasce como `EM_PROCESSAMENTO`, com `UpdateOne` + `$setOnInsert` + `IsUpsert = true`. Se ele já existir, o upsert não altera nada, e o processador lê o estado atual para decidir o que fazer.

### 3. Regras de reprocessamento

| Estado encontrado ao receber a mensagem | Ação |
| --- | --- |
| Não existe | Cria como `EM_PROCESSAMENTO`, chama o motor, grava a decisão, publica e preenche `publicadoEm`. |
| `EM_PROCESSAMENTO` | Execução anterior caiu antes de gravar a decisão. Chama o motor de novo (ele é determinístico, então o resultado é o mesmo) e segue o fluxo. |
| `APROVADA` ou `REPROVADA` **sem** `publicadoEm` | Execução anterior caiu entre gravar e publicar. **Não recalcula**; só publica a decisão gravada e preenche `publicadoEm`. |
| `APROVADA` ou `REPROVADA` **com** `publicadoEm` | Já foi tudo feito. Ignora a mensagem e registra em log como duplicata. |

### 4. Publicação confirmada

O `publicadoEm` só é preenchido depois que o producer confirmar a entrega (`ProduceAsync` concluído com sucesso). O producer faz `Flush` antes do handler retornar.

### 5. Consequência para o consumidor

Como a publicação pode acontecer mais de uma vez (falha depois de publicar e antes de gravar `publicadoEm`), o tópico `credito.propostas.avaliadas` também é *at-least-once*. Por isso a Lambda `despachante-notificacao` **também é idempotente**: o índice único de `auditoria_propostas` impede o registro duplicado, e o erro de chave duplicada é tratado como sucesso.

## Alternativas consideradas

| Alternativa | Por que não agora |
| --- | --- |
| **Transactional Outbox** (gravar o evento numa coleção `outbox` na mesma transação da decisão e ter um *relay* que publica) | É o padrão mais robusto, mas exige MongoDB em *replica set* (para transações) e mais um componente para publicar. Fica registrado como evolução natural. |
| **Transações do Kafka / exactly-once** | Garantem atomicidade só dentro do Kafka; não cobrem a gravação no MongoDB. |
| **Ignorar qualquer proposta já existente** | Simples, mas perde eventos no cenário de falha entre gravar e publicar. |
| **Idempotência via Powertools for AWS Lambda** | Funciona bem, mas o armazenamento padrão é o DynamoDB, que adicionaria mais um serviço ao projeto. |

## Consequências

**Positivas**

- Nenhuma proposta é recalculada nem auditada em duplicidade.
- Nenhum evento de decisão se perde em falhas entre as duas escritas.
- Os cenários de falha viram casos de teste claros (ver specs 04 e 07).

**Negativas**

- Mais lógica no processador (a tabela de reprocessamento).
- O tópico de saída pode ter eventos duplicados, o que empurra a responsabilidade de idempotência também para o consumidor.

## Quando revisitar

Se o projeto evoluir para produção ou para múltiplos consumidores do tópico `credito.propostas.avaliadas`. Nesse caso, avaliar o Transactional Outbox.

## 1. Resumo

Arquitetura de referência **serverless orientada a eventos** (EDA) executada **localmente**, sem custo de nuvem. O projeto simula uma esteira transacional de análise de crédito composta por quatro funções **AWS Lambda em C# (.NET 10)**, emuladas no **LocalStack**, que consomem e produzem eventos no **Apache Kafka** via **Event Source Mapping (ESM)**, persistem no **MongoDB** e são cobertas por testes automatizados com **xUnit**.

---

## 2. Problema e Solução

Em esteiras de crédito com alta concorrência, quatro problemas aparecem com frequência:

1. **Motor de risco acoplado a I/O.** A regra de decisão é determinística, mas costuma ficar misturada com acesso a banco e mensageria, o que dificulta testar e escalar.
2. **Connection storm em serverless.** Quando o tráfego do Kafka cresce, dezenas de instâncias concorrentes de Lambda abrindo conexões sem controle derrubam o MongoDB.
3. **Entrega *at-least-once* do Kafka.** Falhas transitórias reentregam o mesmo evento. Sem idempotência, a mesma proposta é recalculada e auditada em duplicidade.
4. **Escrita dupla (MongoDB + Kafka).** Se a Lambda grava a decisão no banco e falha antes de publicar no Kafka, a reentrega não pode simplesmente "pular" a proposta, senão o evento se perde.

### Solução proposta

- **Domínio puro isolado:** o cálculo de score roda em uma Lambda própria (`motor-regras-score`), sem dependência de rede ou banco, invocada de forma síncrona (`RequestResponse`) pela Lambda orquestradora.
- **Gerenciamento de conexões:** `MongoClient`, `IProducer` (Confluent.Kafka) e `AmazonLambdaClient` são instâncias estáticas criadas fora do handler, reaproveitadas entre *warm starts*, com pool enxuto (`MaxConnectionPoolSize = 5`).
- **Idempotência:** índice único por `idProposta` + upsert com `$setOnInsert`, máquina de estados explícita da proposta e marcação de publicação (`publicadoEm`) para que uma reentrega republique o evento quando a decisão já foi gravada mas não publicada.
- **Observabilidade e consulta:** interface web para inspecionar os tópicos do Kafka e uma Lambda HTTP (`consulta-proposta`) para auditar o MongoDB direto pelo navegador.

## 3. Arquitetura

```mermaid
flowchart TD
    UI["AKHQ (UI do Kafka) / script"] -->|publica evento| T1[["Kafka: credito.propostas.recebidas"]]
    T1 -->|ESM - lote| L1["λ processador-proposta"]
    L1 -->|1. upsert idempotente| M1[("MongoDB: propostas")]
    L1 -->|2. Invoke RequestResponse| L2["λ motor-regras-score<br/>(domínio puro)"]
    L2 -->|3. score + faixa + limite| L1
    L1 -->|4. atualiza decisão| M1
    L1 -->|5. publica decisão| T2[["Kafka: credito.propostas.avaliadas"]]
    T2 -->|ESM - lote| L3["λ despachante-notificacao"]
    L3 -->|6. trilha de auditoria idempotente| M2[("MongoDB: auditoria_propostas")]
    C["Browser / cURL"] -->|GET ?idProposta=| L4["λ consulta-proposta<br/>(Function URL)"]
    L4 --> M1
    L4 --> M2
```

**Ciclo de vida da proposta:** `EM_PROCESSAMENTO → APROVADA | REPROVADA` (+ `publicadoEm` quando o evento de decisão foi confirmado no Kafka).

## 4. Componentes

| Lambda | Gatilho | Evento de entrada (.NET) | Responsabilidade |
| --- | --- | --- | --- |
| `processador-proposta` | ESM em `credito.propostas.recebidas` | `KafkaEvent` | Decodifica o lote, registra `EM_PROCESSAMENTO` com trava de idempotência, invoca o motor via AWS SDK, grava a decisão e publica em `credito.propostas.avaliadas`. |
| `motor-regras-score` | Invocação direta (`RequestResponse`) | DTO próprio (`AvaliacaoScoreRequest`) | Avalia comprometimento de renda vs. valor solicitado, calcula o score, enquadra a faixa de risco (`BAIXO`, `MEDIO`, `ALTO`) e define o limite. Sem I/O. |
| `despachante-notificacao` | ESM em `credito.propostas.avaliadas` | `KafkaEvent` | Persiste uma trilha imutável e idempotente em `auditoria_propostas`. |
| `consulta-proposta` | Lambda Function URL (HTTP GET) | `APIGatewayHttpApiV2ProxyRequest` | Recebe `idProposta` via query string, agrega proposta + auditoria e devolve JSON (404 se não existir). |

As regras de negócio, contratos e critérios de aceite de cada componente estão nas especificações em [`_context/`](./_context).

## 5. Decisões Técnicas

Resumo das decisões. Os detalhes e trade-offs ficam registrados em [`docs/adr/`](./docs/adr).

- **Runtime gerenciado `dotnet10`** (LTS). Native AOT fica fora do escopo inicial e será avaliado depois, medindo cold start.
- **Invocação síncrona Lambda → Lambda** é uma escolha deliberada de estudo para isolar o domínio. Em produção isso tem custo (a orquestradora fica parada aguardando) e acoplamento; a alternativa (motor como biblioteca dentro da mesma Lambda) está documentada na ADR.
- **Chave da mensagem Kafka = `idProposta`**, garantindo ordem por proposta dentro da partição.
- **Producer Kafka com `Flush`** antes do retorno do handler, porque o ambiente da Lambda é congelado entre invocações.
- **Dados sensíveis:** o CPF nunca aparece em logs (mascarado), em linha com a LGPD.

===== scripts/empacotar-lambdas.sh =====
#!/usr/bin/env bash
set -euo pipefail

raiz="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
cd "$raiz"

if [[ -f "$raiz/.env" ]]; then
  set -a
  source "$raiz/.env"
  set +a
fi

arquitetura="${LAMBDA_ARCHITECTURE:-x86_64}"
if [[ "$arquitetura" != "x86_64" && "$arquitetura" != "arm64" ]]; then
  echo "Erro: LAMBDA_ARCHITECTURE inválida '$arquitetura'. Valores aceitos: x86_64 ou arm64." >&2
  exit 1
fi

if ! command -v dotnet >/dev/null 2>&1; then
  echo "Erro: dotnet não foi encontrado. Instale o .NET 10 SDK." >&2
  exit 1
fi

if ! dotnet lambda --help >/dev/null 2>&1; then
  echo "Erro: Amazon.Lambda.Tools não foi encontrado. Instale com: dotnet tool install -g Amazon.Lambda.Tools" >&2
  exit 1
fi

mkdir -p "$raiz/dist"

lambdas="motor-regras-score:src/MotorCredito.Lambda.MotorRegrasScore
processador-proposta:src/MotorCredito.Lambda.ProcessadorProposta
despachante-notificacao:src/MotorCredito.Lambda.DespachanteNotificacao
consulta-proposta:src/MotorCredito.Lambda.ConsultaProposta"

while IFS= read -r lambda; do
  nome="${lambda%%:*}"
  projeto="${lambda#*:}"
  echo "Empacotando $nome..."
  dotnet lambda package \
    --project-location "$raiz/$projeto" \
    --configuration Release \
    --framework net10.0 \
    --function-architecture "$arquitetura" \
    --output-package "$raiz/dist/$nome.zip"
done <<< "$lambdas"

echo "Pacotes gerados:"
ls -1 "$raiz"/dist/*.zip

    [InlineData("MotorCredito.Lambda.DespachanteNotificacao")]

    {
        var projeto = EncontrarProjeto(nomeProjeto);
        var diretorio = Path.GetDirectoryName(projeto);
        diretorio.ShouldNotBeNull();
        var defaults = JsonDocument.Parse(File.ReadAllText(
            Path.Combine(diretorio, "aws-lambda-tools-defaults.json")));

        defaults.RootElement.GetProperty("function-runtime").GetString().ShouldBe("dotnet10");
        defaults.RootElement.GetProperty("framework").GetString().ShouldBe("net10.0");
        defaults.RootElement.GetProperty("configuration").GetString().ShouldBe("Release");
        defaults.RootElement.GetProperty("function-handler").GetString().ShouldBe(
            $"{nomeProjeto}::{nomeProjeto}.Function::FunctionHandler");
    }

    private static string EncontrarProjeto(string nomeProjeto)
    {
        return Repositorio.ListarProjetos()
            .Single(caminho => Path.GetFileNameWithoutExtension(caminho) == nomeProjeto);
    }

internal static class XmlExtensions
{
    public static string[] ReferenceNames(this XDocument documento, string elemento)
    {
        return documento.Descendants(elemento)
            .Select(referencia => referencia.Attribute("Include")?.Value)
            .Where(caminho => caminho is not null)
            .Select(caminho => NomeProjeto(caminho!))
            .ToArray();
    }

    private static string NomeProjeto(string caminho)
    {
        var separado = caminho.Replace('\\', '/');
        return Path.GetFileNameWithoutExtension(separado);
    }
}

===== tests/MotorCredito.Arquitetura.Tests/Repositorio.cs =====
using System.Xml.Linq;

namespace MotorCredito.Arquitetura.Tests;

internal static class Repositorio
{
    public static DirectoryInfo LocalizarRaiz()
    {
        var diretorio = new DirectoryInfo(AppContext.BaseDirectory);

        while (diretorio is not null)
        {
            if (File.Exists(Path.Combine(diretorio.FullName, "MotorAnaliseCredito.slnx")))
                return diretorio;

            diretorio = diretorio.Parent;
        }

        throw new InvalidOperationException(
            "Não foi possível localizar MotorAnaliseCredito.slnx subindo a partir de AppContext.BaseDirectory.");
    }

    public static IReadOnlyList<string> ListarProjetos()
    {
        var raiz = LocalizarRaiz();

        return Directory.EnumerateFiles(raiz.FullName, "*.csproj", SearchOption.AllDirectories)
            .Where(caminho => !caminho.Contains($"{Path.DirectorySeparatorChar}obj{Path.DirectorySeparatorChar}")
                && !caminho.Contains($"{Path.DirectorySeparatorChar}bin{Path.DirectorySeparatorChar}"))
            .ToArray();
    }

    public static XDocument CarregarProjeto(string caminho)
    {
        return XDocument.Load(caminho, LoadOptions.PreserveWhitespace);
    }
}

    [Fact]
    public void Deve_conter_todos_os_projetos_de_src_e_tests_Quando_solution_e_lida()
    {
        var raiz = Repositorio.LocalizarRaiz();
        var solution = XDocument.Load(Path.Combine(raiz.FullName, "MotorAnaliseCredito.slnx"));
        var projetos = solution.Descendants("Project")
            .Select(projeto => projeto.Attribute("Path")?.Value)
            .Where(caminho => caminho is not null)
            .Select(caminho => caminho!.Replace('\\', Path.DirectorySeparatorChar).Replace('/', Path.DirectorySeparatorChar))
            .ToArray();

        projetos.Length.ShouldBe(11);
        projetos.Count(caminho => caminho.StartsWith($"src{Path.DirectorySeparatorChar}", StringComparison.Ordinal)).ShouldBe(6);
        projetos.Count(caminho => caminho.StartsWith($"tests{Path.DirectorySeparatorChar}", StringComparison.Ordinal)).ShouldBe(5);

        var projetosDaSolution = projetos
            .Select(caminho => Path.GetFullPath(Path.Combine(raiz.FullName, caminho)))
            .ToHashSet(StringComparer.OrdinalIgnoreCase);
        var projetosDoDisco = Repositorio.ListarProjetos()

                || caminho.StartsWith(Path.Combine(raiz.FullName, "tests") + Path.DirectorySeparatorChar, StringComparison.OrdinalIgnoreCase))
            .Select(caminho => Path.GetFullPath(caminho))
            .ToHashSet(StringComparer.OrdinalIgnoreCase);

        projetosDaSolution.SetEquals(projetosDoDisco).ShouldBeTrue();
    }
}
